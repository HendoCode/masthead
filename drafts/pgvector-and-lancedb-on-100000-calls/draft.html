pgvector and LanceDB on 100,000 calls

One laptop, 100,000 synthetic transcripts, 40 labeled questions, one retriever interface. p50 latencies: pgvector exact scan 872.9 ms, pgvector HNSW 3.799 ms, LanceDB default IVF-PQ 15.994 ms.

The contact-center-ai repo indexes 100,000 synthetic call transcripts, and its search path needed a store choice. I ran the same 40 labeled questions through one retriever interface against pgvector and LanceDB on an 8-core i5 laptop with 15 GB RAM. The run is dated 2026-10-03; its rendered table lives in results/retrieval/README.md, which records the hardware and the software versions. The full environment is under the results table below.

The bench under test

The labels live in retrieval/labels/queries.jsonl. All 40 records carry the query text, an optional where clause, the relevant call ids, a type, and a derivation predicate. The relevant ids come from the seed-42 generator's own output, before any retriever runs. The four types:

Label types in retrieval/labels/queries.jsonl.
TypenWhat it tests
topical11Naming a call's subject in the corpus's own words.
filter10Constraints the text cannot carry, passed as where. Outcome and date are generator fields and are never spoken.
exact10Verbatim strings. Six are phrases the builder asserts appear in only one category's template; four are ids spoken in the call.
paraphrase9The same intents in other words. The builder asserts each shares at most one content word with its target template, and all nine share none.

The 100,000 rows are a synthetic scale-up: the 1,250-call corpus replicated 80 times with new call ids and a seeded vector jitter of 0.05. The replicas are near-duplicates, each carrying that seeded jitter. Ingest goes in batches of 12,500 rows. Embeddings are precomputed and cached under .cache/embeddings/, one file per embedding model, keyed by text hash; the run embedded the roughly 1,060 unique texts once (nomic-embed-text via Ollama). The ingest and latency timings exclude the embedding step, and the query embedding p50 was 44.140 ms.

One retriever interface sits between that pipeline and the store clients. Each backend plus mode is one row with the same keys: a query, an optional where, k=10, ranked call ids back. A backend that fails becomes a one-line failed row and the others still run.

Two pgvector details are recorded in retrieval/README.md. The HNSW index is partial because the LangChain column has no fixed dimension; it is queried with bench-only SQL and dropped afterwards. The Compose db service sets shm_size to 1gb because Docker's default shared memory is too small for a parallel HNSW build at 100,000 rows.

Two recall numbers

Label recall@10 is capped recall, |relevant ∩ top-k| / min(k, |relevant|), against the generator-derived relevant ids. ann_recall@10 is the overlap of a vector row's top 10 against a brute-force exact top 10 the bench computes itself on the same vectors, the same filter, and the same tie handling; an exact scan scores 1.0 there by construction. The two metrics have different reference sets, and the columns are never subtracted from each other.

At scale 80 the labels still carry the ids computed at scale 1, and every replica of a relevant call counts as relevant. At scale 1 each relevant call has one copy, so the label recall columns read against one copy per call. At scale 80 the replicas make recall measure ranking among near-duplicates, so scale runs compare ingest and latency only. On filter queries, pgvector-hnsw label recall@10 is 0.800 while the exact scan's is 0.700. I did not test why HNSW scores above the exact scan there; tie handling among the 80 near-duplicates is my hypothesis.

This run measured one corpus size, 100,000 rows, on one machine. It says nothing about size scaling beyond that, multi-node behavior, compaction, or versioning.

The pgvector HNSW p95 of 92.885 ms against a p50 of 3.799 ms is driven by the filter queries: the per-type p95 is 134.7 ms on filter queries against about 5 ms for the other types. The pgvector README documents the mechanism: with approximate indexes, filtering applies after the index is scanned, and iterative_scan=relaxed_order keeps walking the graph until k matches pass. The mechanism is consistent with the numbers; the bench did not isolate it. The per-type p50 rows read 71.103 ms on filter queries against 3.349 to 3.477 ms for the other types. LanceDB's vector row sits at 25.356 ms p50 on the same filters.

Index settings and their costs

The LanceDB default row measured label recall@10 0.440 and ann_recall@10 0.025 at 15.994 ms p50. The default is sized for larger data, and I measured it at 100,000 rows. I have not tested whether that explains 0.025. One factor is known: the 80 replicas of each call sit within a seeded jitter of 0.05, so the exact top 10 itself is close to a tie.

Between the default row and the refine_factor=20 row, the recorded settings differ in refine_factor alone. The index stays ivf_pq, cosine, 316 partitions, default nprobes; the two rows share one ingest (146.4 s). refine_factor=20 measured p50 20.282 ms, label recall@10 0.528, and ann_recall@10 0.163. The arithmetic is 4.3 ms at the median for a recall lift from 0.440 to 0.528. refine_factor=1 landed 1.5 ms from the default row's p50 (17.470 ms against 15.994 ms), and one run per config is too few to establish that difference.

The nprobes knob did not move recall. The committed bench notes record exact-top-10 overlap flat at 2/10 across the probe range, from 1 probe to all 316. A separate local run on offline hashed embeddings held at 0.225 at 5, 20, and 50 probes; those embeddings differ from the nomic-embed-text run, so that observation is weak corroboration. The README states the loss is "PQ quantization, which cannot rank near-identical vectors." The two committed observations do not contradict it. As of 2026-10-06, I have not raised num_sub_vectors or changed the partition count in a committed run, and no non-PQ control (ivf_flat or ivf_hnsw_sq) is committed.

A discarded early run

The first result was a 49x gap. It was a non-comparable run, and I threw it out. The rows, the latencies, and the settings behind it are not in the files this post cites.

The bench behind the table records its comparability machinery in retrieval/README.md. Every row records its index and search settings. There is one exact reference row. Embeddings are precomputed and cached, with ingest and latency timings excluding the embedding step. Timing starts after one untimed pass over every query, so a cold cache cannot count against either side.

Choosing at this size

The ingest figures are one measurement per store: 177.6 s into Postgres through langchain-postgres 0.0.17, 146.4 s into LanceDB. The index builds are separate measurements after ingest: 27.180 s for HNSW, 115.4 s for IVF-PQ.

For the vector-search path at 100,000 rows on this corpus, I pick pgvector with its HNSW index: p50 3.799 ms, p95 92.885 ms, ann_recall@10 0.495, and an index built in 27.180 s. 0.495 means HNSW's top 10 missed about half of the exact top 10 on this corpus, and the run did not sweep ef_search beyond 40. The flip is the filtered-vector tail. On where-filtered queries, pgvector-hnsw takes 71.103 ms p50 and LanceDB's vector row takes 25.356 ms p50; if the workload is mostly filtered vector search and LanceDB's filtered p95 of 30.330 ms matters more than a 3.799 ms median, I move to LanceDB. A path that also needs hybrid or BM25 in one store flips the pick outright: the pgvector backend here supports vector mode only, and LanceDB has fts and hybrid rows.

I have not run any of this against a production query mix.

Next tests

  1. A scale-1 rerun, where each relevant call has one copy and label recall measures category discrimination.
  2. A committed non-PQ run (ivf_flat or ivf_hnsw_sq) as the direct check on the PQ diagnosis.
  3. A rescore that collapses the 80 replicas to their seed document id, so ann_recall@10 scores the index on collapsed document ids.
  4. An ef_search sweep on the HNSW index; this run left it at 40 and the bench documents the sweep flag.
  5. Index memory and disk footprint for HNSW against IVF-PQ, which this run did not collect.
  6. A noisy-metadata filter variant, before the filtered p50 figures are quoted as a real lookup cost. The bench's filter metadata is correct and complete; real metadata is entered by humans.
  7. The same suite at larger corpus sizes (planned, not run).

The corpus is synthetic: the fictional Meridian Valley credit union, seed 42, a portfolio mirror of work I did for a credit union. It holds none of the client's systems or data.
