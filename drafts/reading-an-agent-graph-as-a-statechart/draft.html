Reading a LangGraph Agent Graph as a Statechart: Interrupt Flow and Test Coverage

A LangGraph analyst that stops and asks which rate you mean.

There is one place in the contact-center-ai agent where it stops and waits for a person. Ask it for "our average rate" against the synthetic Meridian Valley credit union data (seed 42, a portfolio mirror of work I did for a credit union, holding none of the client's systems or data), and "rate" could mean seven declared metrics, from average_mortgage_note_rate to average_deposit_apy. The agent asks which ones you mean before it runs any SQL.

My background is in modeling, statecharts in particular, so I read this graph as a statechart. This post is that reading: how it maps onto the LangGraph code, where it stops fitting, and what it changed in how I check tests. LangGraph is not a statechart implementation; it has no orthogonal regions and no history states. The statechart is a way of reading the graph, and that is all I am claiming for it.

How the Parent Graph and the Analyst Subgraph Work

The parent graph is in agent/graph.py. classify reads the question and writes route: a CALL-\d{5} match goes straight to summarize_call with no model call, anything else gets one structured LLM call. A conditional edge on s["route"] fans out to retrieve, summarize_call or resolve_metric, and all three join at ground, then answer, then END. ground checks every cited call id against the vector store and, on the metric route, requires SQL and declared metrics; it uses no LLM. answer formats what is in state and adds no facts.

resolve_metric is the analyst subgraph in agent/subgraphs/analyst.py. Its three nodes share the parent's AgentState, so nothing is mapped at the boundary. disambiguate runs match_terms against a YAML term list (agent/data/ambiguous_terms.yml; starter terms: rate with 7 candidates, balance with 10, lcv/ltv with 2), skipping terms already resolved. If a term still has several candidates after the qualifiers vote, it writes term and candidates and the router sends it to clarify; otherwise the metrics merge into metric_names and it goes to execute.

clarify is the only node in the graph that calls interrupt(). The payload has kind clarify_metric, version 1, the term, a prompt, the options and multi_select: true. The caller sees it under result["__interrupt__"] and answers with Command(resume={"choices": [...]}) on the same thread_id. An invalid answer within MAX_REASKS = 2 only bumps clarify_attempts and loops back. A valid answer, or the re-asks running out, merges the chosen ids (or every candidate) into metric_names and returns to disambiguate, because one question can carry a second ambiguous term. execute then calls the MCP tool query_metric with the names, or ask_the_analyst with the raw question if no term matched.

The exhausted re-asks run every candidate. The code comment says "rather than blend them or pick one." Blending a mortgage note rate with a deposit APY gives a number nobody at a credit union would use, and it looks like a real answer. Picking a default is a guess, and avoiding a guess is the reason the interrupt exists. Failing the run or escalating are not discussed in the design doc; my reasoning is that the person answering the interrupt already is the human, and running every candidate keeps the run moving, labels every number, and guarantees the loop exits.

How Paused Agent States are Persisted in Postgres

The paused run is stored in Postgres. agent/checkpoint.py opens an AsyncPostgresSaver on the same Compose db the rest of the stack uses, its tables in a langgraph schema set through search_path in the connection string. The design doc rejected SqliteSaver as a second engine when every route already needs Postgres. The subgraph is compiled without its own checkpointer, so it inherits the parent's, which is why its interrupt surfaces in the parent run. Tests use InMemorySaver and langgraph dev keeps state in memory; neither survives a restart.

Think of the checkpoint as a saved game and the thread_id as the save slot: the run stops, the process can exit, and loading the same slot later picks up where it stopped. The analogy stops being accurate in two places. A game saves when the player asks, while LangGraph checkpoints at every super-step without being asked. And the caller mints the slot id, so two callers that share a thread_id share a save.

When clarify pauses, the checkpoint holds the AgentState keys at that moment under the caller's thread_id, a UUID4 the caller mints. If the process restarts before anyone answers, the thread stays paused; a new process rebuilds the graph and resumes on the same thread_id. There is no expiry, and handling abandoned threads is still to build. I have not run a restart drill against a long-lived deployment, and none of this is in production.

Mapping Graph Nodes, Edges and State to Statechart Concepts

Drawing one statechart state per node would put states where nothing waits. classify, retrieve, ground and answer run to completion and hand off. LangGraph checkpoints at every super-step, so each node boundary is a saved position, but no outside event can arrive at one. So I read the graph this way: AgentState is the extended state, and term, candidates, resolved_terms and clarify_attempts are the context the guards read. The nodes are actions. The lambdas passed to add_conditional_edges are the guards, which SCXML would write as the cond on a transition.

Read that way, the graph has one resting state, inside clarify, where it waits for the human. I call it AwaitingChoice. Building the payload and calling interrupt() is its entry behavior, and the resume Command is the external event that moves it on. disambiguate is a decision point. execute is the action on the way out of the composite state.

Think of the graph as a clinic with one waiting room. Every other node is a corridor: a patient walks through it and something happens on the way, such as a form being checked or a record pulled, but nobody sits down. AwaitingChoice is the waiting room, the only place the run stays until someone outside calls it forward. The analogy stops being accurate on storage. A waiting room holds the patients themselves, while here the process holds nothing between runs and the Postgres checkpoint holds the state, which is why a restart does not empty the room.

Modeling the Re-ask Loop as an External Self-Transition

In a statechart, a state waiting for an event does not re-run its entry when the event arrives. In LangGraph, clarify restarts from the top on resume, so everything before interrupt() runs again. The design handles this with two rules: nothing with side effects comes before the interrupt(), and the call is never wrapped in try/except. Building the payload is a pure function of state, so running it twice is harmless. A statechart guarantees the entry runs once; here you make the entry idempotent yourself.

Think of resuming as a clerk who rereads the form from its first line after every interruption. Reading the ID field twice costs nothing, and stamping the form twice does, so everything above the interrupt() has to be as safe as reading. The analogy stops being accurate at memory. A clerk remembers having read the form, while the node keeps nothing from the earlier run except the checkpointed state.

The re-ask is a real second run of the node: a new step, a new interrupt(), and a prompt that ends "Answer with option ids from the list." So I draw it as an external self-transition, one that leaves the state and enters it again, guarded on clarify_attempts <= MAX_REASKS. SCXML lets a transition be declared internal or external; an internal one does not exit and re-enter its source. As far as I know, LangGraph gives you only the external kind.

Checking Whether the Analyst Subgraph Behaves as a Composite State

Reading resolve_metric as a composite state holds for the structure: one entry (the classify edge when the route is resolve_metric), one exit (execute to END, then the parent's edge to ground), and the loops stay inside. It breaks in three places. The parent has no transition on the composite that fires from whichever substate is active, so nothing pulls a run out of clarify early. There is no error or cancel edge; an exception in execute fails the run. And the subgraph has no data scope of its own, since it reads and writes the parent's keys. Command has a graph field that can send control to the parent from inside a subgraph; this graph does not use it, so END is the only exit.

Coming back into clarify after a resume can look like a history state. It is not one. The run resumes by replaying from the checkpoint, and you cannot leave the box and return to its last active substate.

Why Counting Coverage by Edge Overstates What Is Tested

The exhausted fallthrough has no edge of its own. It leaves on the same clarify → disambiguate arrow as a valid answer; the difference is a branch inside clarify, and the router only checks whether term is cleared. A count by edge sees the valid-resume test, ticks that edge, and reports the exhausted path as covered. The self-loop has the mirror problem: one invalid answer ticks it and says nothing about what happens past the limit.

Think of checking a delivery route by confirming that every road on the map was driven once. A road with a toll booth that has a lane for a valid pass and a lane for a bad one counts as driven after one trip through the valid lane. The analogy stops being accurate on what picks the lane. A driver chooses a lane on the spot, while clarify is steered by clarify_attempts, a counter built up over the earlier visits, so the path past the limit only exists after several trips around the loop.

Testing the Re-ask Limit: What Happens After Two Invalid Answers

The test that pins the re-ask boundary is committed, in tests/agent/test_interrupt.py. It matters because when this path is wrong the result looks like success: no error, just an answer built from every candidate that nobody chose. With MAX_REASKS = 2, the first ask plus two re-asks run, and the third bad answer falls through.

async def test_after_two_re_asks_every_candidate_runs(make, toolbox):
    graph, _ = make("resolve_metric")
    cfg = config()
    result = await graph.ainvoke({"question": "what is our average rate?"}, cfg)
    for _ in range(2):  # two invalid answers: asked again each time
        result = await graph.ainvoke(Command(resume={"choices": ["nope"]}), cfg)
        interrupt_payload(result)

    out = await graph.ainvoke(Command(resume={"choices": ["nope"]}), cfg)  # third: give up

    assert "__interrupt__" not in out
    assert toolbox.tool_calls("query_metric") == [{"metrics": RATE_IDS}]
    assert out["metric_names"] == RATE_IDS

RATE_IDS is the seven rate candidates read from ambiguous_terms.yml, so the test tracks the data file. make builds the graph with the fake LLM and a stub toolbox that records calls; config() mints one thread_id. This ran green with the other 37 agent tests on 2026-10-06, offline.

One gap this does not close: you cannot tell from the output how a term was resolved. AgentOutput has no field for whether the user chose or the re-asks ran out, and a user who picks all seven in YAML order gets an identical result. Today the only way to tell is to count the clarify_metric interrupts in the checkpoint history for that thread_id, or the clarify runs in the LangSmith trace. The fix I have in mind is a per-term resolved_by: "user" | "exhausted" field in the output contract that the eval can check. I have not built it.

Building a Coverage Table for Your Own Graph in Six Steps

I started with a hand sketch; the design doc had an ASCII drawing of the graph before any code existed, and it still sits in the graph.py docstring. Sketching by hand comes first because you name each event and guard before any tool draws it. When I ran get_graph().draw_mermaid() on 2026-10-06 (langgraph 1.2.12), I was looking for the guards and the wait state. The export drew the conditional edges as dotted arrows with no guard labels, the subgraph as one opaque node, and nothing for the interrupt(). The conditions live elsewhere: a regex, an LLM call, the qualifier vote in a YAML file. So the export can check a sketch, and the sketch has to come from you. To turn a sketch into a coverage table:

  1. List every edge from the code, since the drawing is the thing you are checking. Give each conditional edge one row per value its router can return.
  2. Add the transitions a diagram tool will not draw: interrupt and resume, and resume after a restart if you claim it works.
  3. Write the guard on each row in plain words. Split every "or" into its own row, and give a bounded loop one row per counter value plus "past the limit".
  4. Put a test or eval id against each row. A row counts only if the test asserts the transition through route, the interrupt payload or metric_names; a good final answer that passed through the edge does not count.
  5. Mark which runner covers each row, offline or live. Offline covers the wiring; only a live run shows whether the model picks the path.
  6. Any row without an id is a gap. Write the test, or write down that you are accepting the gap.

I came to this from statechart tooling. Earlier in my career I built Eclipse tooling in Xtext for ECharts, a state-machine language derived from UML Statecharts. I worked on the grammar and editor; I never shipped systems written in ECharts. The comparisons in this post rest on SCXML and XState, which document their constructs publicly.

Verdict: When to Read a LangGraph Graph as a Statechart

For a LangGraph graph with a human-in-the-loop interrupt, I would read nodes as actions, router lambdas as guards and the state type as extended state, and draw one wait state per interrupt(). That puts the restart-on-resume behavior where you would look for it, and the interrupt check becomes a test of whether the guards put the machine into its one wait state when they should. The composite-state part depends on a single exit; it gets weaker for a graph that uses Command's graph field to jump to the parent from inside a subgraph.

The broader observation is about coverage. With statecharts the arrow is only half of a transition, and the condition matters just as much. A coverage count that only looks at arrows will report paths as covered when no test ever ran them; reading my own graph this way sent me back to the test file, where the boundary tests I thought were missing had been sitting since the agent landed.

The code is in HendoCode/contact-center-ai. Start with agent/subgraphs/analyst.py and docs/design/agent-graph.md, then build the row-per-guard table for your own graph and see which rows come up empty.
