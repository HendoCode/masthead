Semantics Parity Check: Five Metrics Compared Across Postgres, Snowflake and Databricks

Five metrics from the semantic layer ran on Postgres, Snowflake and Databricks and returned the same values within stated tolerances. This post covers how the check runs, what the saved SQL shows, what the Apache Ossie export loses, and what the check did not cover.

The first full live run of the agent evals in contact-center-ai scored 0.00 on SQL. The per-item export showed why: every metric item had answered with an error, a Postgres syntax error at or near a backtick in FROM `ccai`.`marts`.`f_account_snapshot`. The manifest that MetricFlow reads had last been written by a Databricks build, which quotes relations with backticks, and the metric tool ran that SQL against the local Postgres. The cause was the environment. The dialect difference was still real, and it raised a question I could now test: do the metric definitions return the same numbers on all three warehouses?

This post reports one parity check. make parity ran five of the 43 metrics in the semantic layer on Postgres, Snowflake and Databricks, against one synthetic dataset (a fictional credit union, seed 42; the repo is a portfolio mirror of work I did for a credit union), on two dates: 2026-10-06 and 2026-10-07. The Snowflake account is a trial account. The results files do not record which Databricks edition ran. All five metrics agreed within tolerances set per metric. Nothing here says the numbers would match for the other 38 metrics, a larger dataset, or your schema.

How Parity Is Checked: One Metric Definition Compiled for Three SQL Dialects

The semantic layer is dbt plus MetricFlow. Each metric is declared once in olap/dbt/models/marts/semantic/metrics.yml, and 21 of the 43 carry a filter on a line-of-business discriminator, product.lob. Think of that file as source code, MetricFlow as a compiler, and each warehouse as a target machine, like building one program for x86 and for ARM. The analogy stops being accurate at testing: a compiler is checked against a large test suite, and this check is five queries on one dataset, so it says these five agree and nothing about the compiler as a whole.

tools/parity.py takes each target in turn. It copies that target's semantic manifest into place, runs mf query for the five metrics, and reads back one CSV row. It then runs the query a second time with --explain to save the SQL MetricFlow generated for that warehouse. When the last target is done, it restores the manifest that was there at the start. The restore matters because a leftover manifest from another warehouse is what broke the eval run above.

Snowflake and Databricks credentials come from 1Password through tools/warehouse-run.sh, so no .env file is populated. Snowflake authenticates with a key pair and has no password field.

Five Metrics and Their Tolerances: Exact Counts, Cents for Money, 1e-4 for Rates

The five are a count (call_volume), an average filtered to mortgages (average_mortgage_note_rate), two filtered sums (banking_available_balance and credit_card_outstanding) and one ratio (first_contact_resolution_rate). A comment in parity.py gives the tolerance rule: "Counts are exact; monetary amounts to the cent; rates/ratios to 1e-4." The files do not say why these five were chosen.

Think of a tolerance as the allowance on a machined part: a part within 0.01 of nominal passes. The analogy stops being accurate where the allowance comes from. A machinist's tolerance follows from what the part must do, and these follow from the type of number. A tighter or looser check is a one-line change in METRICS in parity.py.

SQL Differences Between Dialects: Relation Quoting and One Cast Type

Diffing the three saved files for 2026-10-07 shows the same structure in each: three CTEs, five subqueries joined with CROSS JOIN, a LEFT OUTER JOIN from the account snapshot to d_product on product, and a WHERE product__lob = 'mortgage' filter (or 'banking', or 'cards') on the three line-of-business metrics. Two things differ.

The first is how relations are quoted. The saved files replace the real database names with <name>, so the fragments below show the pattern.

Postgres:    FROM "contactcenter"."marts"."f_interaction" interactions_src_10000
Snowflake:   FROM <name>.<name>.f_interaction interactions_src_10000
Databricks:  FROM `<name>`.`marts`.`f_interaction` interactions_src_10000

The second is the cast type in the ratio. Postgres writes AS DOUBLE PRECISION. Snowflake and Databricks write AS DOUBLE. In all three files the ratio is CAST(SUM(__first_contact_resolved_calls) ...) / CAST(NULLIF(SUM(__call_volume), 0) ...), so float division and a zero denominator that returns null are in the generated SQL on every target.

That is the whole list for these five metrics. The five metrics' SQL contains no date functions, so this run says nothing about how the dialects handle dates. The dbt models follow portability rules (no :: casts, no to_char, use dbt.dateadd and dbt.datediff), but the parity run does not exercise time dimensions.

Ossie Export: What the Interchange File Kept and Dropped

Apache Ossie (incubating, formerly Open Semantic Interchange) defines a vendor-neutral YAML format for semantic models. Its spec was at 0.2.0.dev0, marked draft, when the repo's notes checked it on 2026-10-02. The repo's export was converted from the dbt semantic manifest with the Apache converter, ossie-dbt msi-to-ossie, at commit b6c702e. The export has 11 datasets and 43 metrics and passes the upstream validator.

Think of the export as a translation of a manual in which every sentence survived and a footnote that says which units to use was dropped. The text reads fine and the result can be wrong. The analogy stops being accurate in two ways: the translator here is a converter with fixed behavior, and the parity check did not run the exported expressions, so the wrong result is predicted from reading them.

Three issues turned up. First, the line-of-business filter points at product__lob, which is a MetricFlow join path. account_snapshot has no field by that name. Twenty-one filtered metrics are affected, plus two built from them. Second, call_volume, responses and rate_locks_count all export as SUM(1) with no dataset qualifier, so a consumer cannot tell which dataset each one counts. Third, ratios lose MetricFlow's float division: the export writes (num) / (den), and on an engine with integer division such as Postgres, first_contact_resolution_rate would truncate to 0. A zero denominator would raise an error where MetricFlow returns null. That third issue is the same cast the parity files show above.

Some constructs have no Ossie equivalent and are dropped: time_granularity, the default aggregation time dimension and metric labels. A metric's type is inlined into one expression, so net_member_liquidity no longer references its two input metrics. The dataset source carries the Postgres relation name only. As of 2026-10-06 none of the three issues had been reported upstream.

Limits of the Parity Check: Untested Metrics, Scale, Dates and Accounts

The other 38 metrics did not run, including the derived metrics net_member_liquidity, member_lifetime_value and nps, and the ratio weighted_mortgage_portfolio_rate. Only one of the repo's interest-rate metrics, average_mortgage_note_rate, was in the check. The dataset is one synthetic credit union with a single month-end snapshot (2026-08-31) per account, so there is no slowly changing history, no daily refresh and no date function in the SQL. Nothing measured scale, timing or cost. Snowflake was a trial account, the Databricks edition is unrecorded, and the two runs are on consecutive dates.

The comparison itself looks at values only. parity.py diffs the numbers against tolerances and saves the SQL, and nothing asserts on the SQL text. A dialect difference that returned the same numbers on this data would pass. The parity check never executed the Ossie export, so its three issues come from reading its expressions.

Verdict and Reproduction: Run the Parity Check on Your Own Metrics

For these five metrics on this dataset, MetricFlow compiled one definition into three dialects that returned the same values within tolerance, and the SQL differed only in relation quoting and one cast type. I would keep MetricFlow as the source of truth and use the Ossie export only to move definitions between tools, because the export's expressions give different numbers if a consumer executes them directly. That changes when the three issues are fixed upstream and the export passes the same parity check.

To repeat the check, run make parity in the repo, read results/semantics/ for the values and the saved SQL, and compare them before you quote any number from this post.
